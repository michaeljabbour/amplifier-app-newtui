## B7 — ready-for-user notifications

### Proven in this repository

- `AttentionCenter` is the single normalized record source for bell and OSC
  desktop delivery. Its deterministic `event_id`, current-state pointer and
  acknowledgement state persist in per-session `attention.json` through
  `AttentionStore`.
- Record and acknowledgement updates now hold one advisory interprocess lock
  across reload, mutation and atomic replacement. Two pre-bound centers cannot
  lose each other's events, and an acknowledgement cannot move backward when a
  stale writer arrives later.
- Rebinding a fresh center to the same session hydrates the durable IDs, so
  the same transition returns `is_new=False` after a restart/reconnect.
- Completion, approval/clarification, submitted-turn failures, provider error
  notices, and failed child lanes reach the attention boundary. Retry,
  throttle and deliberate cancellation do not masquerade as errors.
- Every newly minted record is best-effort scheduled onto the real Amplifier
  hooks bus as `attention:recorded`; the payload carries `event_id`,
  `session_id`, reason, timestamp and sanitized notification text. Hook
  delivery failures are swallowed because the persisted `AttentionRecord`, not
  a fire-and-forget hook, is the correctness boundary.
- Delivery suppression no longer erases the record. A muted session remains
  durable/queryable; the app emits a correlated `attention:acknowledged` event
  after the human resumes or answers. The legacy external push hook is always
  stripped, including from user/deferred overlays; persisted global
  suppression also disables the app-owned off-machine sink.

Evidence: `ui/notifications.py`, `kernel/file_lock.py`,
`kernel/attention_store.py`, `kernel/attention_push.py`,
`kernel/runtime.py::publish_attention*`, `tests/test_ui_notifications.py`,

### Destination closure and remaining capability boundary

The prior mounted `amplifier-bundle-notify@v0.2.0` module listened to a turn
event and dropped additive record/session IDs before HTTP, so it could not
close destination identity or acknowledgement. It is no longer mounted by the
wrapper bundle, and `RealRuntime` no longer emits a compatibility completion
projection. That removes the independent producer and its duplicate-risk
boundary.

`kernel/attention_push.py` is now the app-owned destination. It consumes only
the canonical `attention:recorded` and `attention:acknowledged` hook events.
The record's stable `event_id` maps deterministically to a 64-character,
ntfy-safe SHA-256 sequence ID. Publish sends that value as `X-Sequence-ID`, so
a retry/reconnect addresses the same destination sequence; acknowledgement
uses the identical mapping with `PUT /<topic>/<sequence-id>/clear`. Those are
ntfy's documented [update/deduplication and mark-read-and-dismiss
operations](https://docs.ntfy.sh/publish/#updating-deleting-notifications).

The handlers return immediately, keeping HTTP latency/failure off the
Amplifier hooks bus. Advisory publishes enter a bounded FIFO; terminal clears
use a separate coalesced correctness lane. Acknowledgement marks the event
terminal, removes any queued publish, and suppresses a later replay, so a stale
`attention:recorded` event cannot resurrect a cleared notification. Distinct
clears are retained even when the publish FIFO is saturated. Topic is environment-only,
validated against ntfy's 64-character topic shape, and never included in app
logs; failure logging is content-free even when debug is enabled. Remote
servers require HTTPS; HTTP is permitted only for an
explicit localhost/loopback development endpoint. Focused tests
use a mocked HTTP sender to prove method, ordering, headers, stable ID reuse,
exact clear URL, config/env precedence, failure containment, and secret/body
log redaction. This pass did **not** send to a live ntfy server or validate a
specific mobile client's rendered tray behavior, so the claim is the
deterministic local transport contract rather than live-delivery proof.
