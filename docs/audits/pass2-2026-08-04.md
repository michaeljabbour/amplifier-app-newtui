## Method

Same as the baseline: enumerate the donor's surface, match each capability to
this repo's seams, judge **capability** parity rather than code parity, cite
`file:line` on both sides. Three additions this time:

1. **The donor was re-fetched** before auditing (`git fetch origin`), so the
   comparison is against the donor's live `main`, not a July snapshot. The
   baseline's donor tree was 3 weeks stale by the time this pass ran.
2. **Verdicts on the shipped binary, not just the source.** The CLI surface was
   re-enumerated from `amplifier-tui --help` at `7030527`, so a command that
   exists in source but isn't registered can't read as present.
3. **The baseline's own unfiled rows were re-checked.** Pass 1 recorded 10
   `MISSING` rows in lane 1 but filed only 4 of them as tracked gaps. The six
   that were never filed carry no gate row and therefore no disposition — so by
   the loop's own rule (*a gap already carrying any disposition is not new*)
   they are new, and this pass registers them rather than letting them stay
   invisible to the owner.

### Could not determine (explicitly not filed as a gap)

- **Agent-declared `agents:` sub-delegation access control.** The donor changed
  here after the baseline (`session_spawner.py:319-360`, `6c3fd86`): an agent
  declaring `agents: none` / `agents: [a, b]` must have that honored against the
  **live** registry, not just the static snapshot. This repo has no live-registry
  propagation block at all (`kernel/spawner.py` names `agents` only as
  `agent_configs`, `:162,198,320-322`), so the donor's bug cannot exist here —
  but whether an overlay's `agents:` declaration is *enforced* below the app seam
  by foundation could not be established from this repo's code. **Filing this as
  a gap would be a guess.** It is written down here instead, which is what the
  baseline did with its own row 32 and row 34. Resolving it needs a foundation-side
  read, not another app-side pass.

## Lane 3 — runtime & composition

Zero wholly-missing runtime capabilities at the baseline; still zero. One new
divergence, created by a donor policy change:

| Gap | Capability | Donor cite | Target status | Verdict | Sev |
|---|---|---|---|---|---|
| `118` | **Fail-loud module activation** — a declared module that fails to download/activate aborts session start, with `AMPLIFIER_ALLOW_PARTIAL_BUNDLE=1` as the explicit opt-out | `lib/bundle_loader/prepare.py:39` (`_ALLOW_PARTIAL_ENV`); `commands/run.py:17,185-196` (`ModuleActivationError` → panel → `sys.exit(1)`) | starts **degraded** and says so: `kernel/session_factory.py:101-120` (`degraded_notice`, names every failed module), fatal only when *no* provider mounts (`:95-98`, `:474`) | PARTIAL | Med |

This one deserves a real decision rather than a reflexive port. The donor's
argument is stated in its own commit: *"a session that starts without a tool the
user's bundle declared is a session that will fail later, further from the cause,
in a way the user reads as 'the model ignored me'."* This repo's counter-argument
is equally deliberate and is already in the code: a TUI that refuses to boot is a
worse failure than one that boots and names what's missing, so ADR-0007 swallows
mount errors for resilience and `degraded_notice()` exists precisely to keep that
honest. **Both are defensible.** The owner picks; `rejected` is a first-class
answer here.

Also checked, no gap filed: provider-source precedence and dangling-install
repair (`ad69c69`, `145ba2e`) — this repo reaches the same end state through
preflight verification (`kernel/preflight_verify.py:314` `verify_provider`) plus
`doctor` repair guidance (`fa10e50`) and `reset --reinstall` (`main.py:1782`).
Different mechanism, same protection; that is a PARITY verdict under this audit's
own rules.
